# ORX 交接文档 - 2026-05-27

## 本次交付

本次提交围绕 Trellis/PD Clarification 人工澄清流程做了一个小闭环增强：当用户在澄清卡点处输入“需求确认”“方案确认”“继续下一个流程”等短确认语时，ORCH 不再把该输入当作补充需求回灌给同一节点重新执行，而是将澄清视为完成，并继续调度下一个工作流节点。

## 改动范围

- `src/clarificationState.ts`
  - 新增 `isClarificationContinueCommand`，用于识别用户的短确认/继续类指令。
  - 新增 `nextRuntimeAfterClarificationConfirmation`，用于在用户确认澄清完成后把 `nextIndex` 推进到下一节点，并把确认记录写入 `upstream`。
- `src/App.tsx`
  - 在澄清门控提交逻辑中优先识别“确认继续”类输入。
  - 命中确认语后清空输入和错误状态，关闭澄清门控，追加聊天与日志记录，并调用 `continueWorkflow` 继续后续流程。
- `src/clarificationState.test.ts`
  - 增加确认语识别测试。
  - 增加确认后推进下一节点的运行时状态测试。

## 用户可感知行为

原行为：

- 用户在 Trellis 澄清节点输入“需求确认”等短句时，系统会把它当作新的澄清补充信息，并重新运行当前 Clarification 节点。

现行为：

- 用户输入“需求确认”“方案确认”“继续下一个流程”“执行下一个流程”等短句时，系统会确认当前澄清已完成，并继续执行下一流程节点。
- 如果用户输入的是实际补充内容，例如“还是需要补充错误提示样式”，仍会按原逻辑回灌给当前澄清节点继续处理。

## 验证建议

已覆盖的自动化验证：

- `npm run workflow:selftest`
- `npm run build`

建议手动回归：

1. 启动应用并进入一个包含 PD Clarification/Trellis 的工作流。
2. 让流程停在澄清门控处。
3. 输入“需求确认”，确认系统继续到下一个节点。
4. 再次回归一个普通补充输入，例如“请补充异常状态下的按钮文案”，确认系统仍停留在当前澄清节点并重新执行。

## 风险与注意事项

- 确认语识别目前是正则匹配，覆盖的是简短自然语言命令。若后续需要支持更多口语化表达，应优先补充测试用例，再扩展正则。
- `nextRuntimeAfterClarificationConfirmation` 会把确认信息写入 `upstream`，方便后续 Agent 知道该澄清是由用户明确确认后推进的。
- 该改动只影响 Clarification 人工门控处的用户输入处理，不改变普通工作流调度、审批、回滚或产物保存逻辑。

## 交接给后续开发

后续如果继续增强 Trellis 澄清体验，可以优先关注：

- 将确认语识别列表抽成更易维护的配置或常量。
- 在 UI 上增加显式“确认并继续”按钮，减少对自然语言确认语的依赖。
- 为聊天日志中的 ORCH 提示增加更统一的文案规范。
